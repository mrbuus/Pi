# T19 сонголт ялгах засварын QA

Бүх өгөгдлийн сангийн туршилт тусгаарласан локал PostgreSQL 3367 дээрх `T19-SYN-*` хиймэл мөрүүдэд хийгдсэн. Бодит контентын сан ашиглаагүй. C болон танигдаагүй хувилбарын `statementText`/`correctAnswer` талбарыг metadata шалгалтаас өмнө сонгохгүй; хадгалсан session-д орсон бодлогын текстийг уншихгүй, засахгүй.

Парсер 60 системчилсэн хэлбэр болон nested LaTeX доторх хуурамч label, `{}` баланс, escaped brace, shared math, `\hspace`, латин/кирилл жижиг үсэг, parenthesized label, option доторх label зэрэг 10-аас олон өөр синтаксийн edge case-тай нийлээд 83 тестээр шалгагдсан. Хуучин үсгэн хариултын үнэлгээ өөрчлөгдөхгүйг тусгай regression тестээр шалгасан. KaTeX-ийн локал хувилбараар ялгасан 206 томьёог `throwOnError: true`, `strict: 'error'`, `trust: false` тохиргоотой рендерлэхэд алдаа гараагүй. Нэмэлт синтетик буруу команд KaTeX шалгалтад унаж `REVIEW_REQUIRED` болсон; тэнцвэргүй brace болон LaTeX бүлгүүд автоматаар засагдаагүй.

Синтетик DB дээрх dry-run-д нэг зөв мөр засахаар төлөвлөж, зөв бус бүтэц/KaTeX-ийн улмаас дөрвөн мөрийг эргэлзээтэйд үлдээж, C хувилбар болон хадгалсан session-тэй гурван мөрийг алгассан. Dry-run нь `ProblemChoice` үүсгээгүйг өгөгдлийн сангаас шалгасан. Дараа нь тусдаа synthetic candidate-ийг `--commit --confirm-offline-write --flag-review` тохируулгатай туршсан: нэг мөрд таван сонголт үүсэж, `correctAnswer`-д таарсан ганц `isCorrect`, `order` 0–4 байв. KaTeX/brace шалгалтад унасан мөрүүдэд сонголт үүсээгүй, харин `REVIEW_REQUIRED` болсон. Хадгалсан session болон C мөр өөрчлөгдөөгүй.

Commit туршилтын нөөц файл `/tmp/t19-choice-backup-20260927-05.json`-д, `0600` эрхтэйгээр, transaction-оос өмнө бичигдсэн. Нөөцийн замыг бодит repo root-той canonical path-аар шалгадаг; repo доторх зам болон repo дотор заасан symlink-ээр орсон зам хоёуланг нь туршиж татгалзуулсан. Transaction алдаа гарсан эсвэл үр дүн тодорхойгүй үед нөөц файлыг хадгална.

Commit хийхийн өмнө `--maintenance-window` эсвэл `--confirm-offline-write` шаарддаг. `TestAttemptSession`-ийг сериалчлах transaction шалгадаг ч `startSession` ижил lock ашигладаггүй. Иймээс бодит засвар хийх үед эзэн шалгалтын шинэ session үүсгэлтийг бүх засварын хугацаанд тусад нь унтраах ёстой; скрипт дангаараа энэ race-ийг хаах боломжгүй.

Шалгалтын үр дүн: `npx tsc --noEmit` OK; API Jest 58 suite / 650 тест OK; `npm run build` OK; T19-ийн хоёр файлд ESLint OK; CLI `node --check` OK. Энэ тайлан production өгөгдөлд ажиллуулсны баталгаа биш.
