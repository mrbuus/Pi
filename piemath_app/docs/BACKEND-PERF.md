# API-ийн хурд ба найдвартай байдал (2026-11-03)

Вэб ба Piemath апп нэг NestJS API, нэг PostgreSQL ашигладаг. Энэ баримтад хоцрогдол,
алдааг багасгах ажлын хэмжилт, өөрчлөлт, deploy-ийн тэмдэглэлийг бичив.

## Хэмжилтийн арга

- Зөвхөн локал хуулбар `pimn_scan` (127.0.0.1:5544). Прод, `pimn_v2`-д хүрээгүй.
- API-г `PORT=3880 DB_SLOW_QUERY_MS=0` горимд асааж, endpoint бүрийг дангаар нь дуудсан
  (дулаацуулсны дараа 7 дуудлагын медиан). Ачааллын тест (k6) ажиллуулаагүй.
- **Query-ийн тоо** нь гол үзүүлэлт: локал ӨС-ийн нэг round trip ~0.1 мс, харин
  EC2 → RDS дээр ~0.5–1 мс тул прод дээрх хоцрогдол ≈ query тоо × RTT.
- Мутаци хийсэн хэмжилтийн мөрийг (сесс, дүн, Attempt, ирц, аудит, Problem статистик)
  хэмжилтийн дараа хуулбараас буцааж цэвэрлэсэн.
- Индексийн хамрах хүрээ: бүртгэгдсэн 120 өвөрмөц SELECT/UPDATE/DELETE-ийг
  `SET enable_seqscan=off; EXPLAIN (GENERIC_PLAN)`-аар шалгав. Ганц `User.role`-оор
  шүүх (ажилтны жагсаалт, ~700 мөр) л индексгүй — ач холбогдолгүй.

## Өөрчлөлтүүд

1. **Илгээлт (submit)-ийн алдааны дэвтэр араар.** Буруу бодлого бүрд ~8 query
   (transaction + мөр түгжээ) дараалан явж хүсэлтийг барьдаг байв. Одоо
   `MistakeCollector.collectAttemptsInBackground` хариу буцсаны дараа дараалан
   цуглуулна; алдаа гарвал мөр pending үлдэж 5 минут тутмын `retryPending` авна.
   Унтрахдаа (SIGTERM) эхэлсэн цуглуулгыг дуусгаж байж гарна. Оройн өөрийн тайлан
   (`attempts.service`) мөн адил.
2. **Давхар submit-ийн уралдаан.** Зэрэг ирсэн хоёр илгээлт хоёулаа `IN_PROGRESS`
   уншаад хоёулаа дүгнэж, Attempt мөр ба Problem статистик давхардаж болдог байв.
   Одоо transaction-ийн ЭХНИЙ үйлдэл `status = IN_PROGRESS` нөхцөлтэй update; хоёр
   дахь нь түгжээ хүлээгээд P2025 → бүхэлдээ rollback. Submit → дараалсан давталттай
   ижил `409`; хугацаа дуусах үеийн autosave/heartbeat/start → хадгалсан дүнг буцаана.
   Локал дээр 3 зэрэг submit: `201, 409, 409`, Attempt 40 (давхардалгүй).
3. **Start:** шинэ эхлэлтэд бүтэн тестийг (40 бодлого + сонголт + бодолт) transaction-ээс
   гадуур давхар татдаггүй болов. Шалгалт эхлэх оргил үед query 28 → 18.
4. **Аудит нэг INSERT-ээр.** «Бүгд ирсэн» 41 сурагчид 41 зэрэг INSERT явж pool-ын (15)
   бүх холболтыг эзэлдэг байв → `AuditService.recordMany` (ирц, гэрийн даалгаврын тэмдэглэгээ).
5. **Кэш (процессын санах ой, богино TTL, single-flight, `common/ttl-cache.ts`):**
   - томьёоны жагсаалт, бүлэг — 60 с, томьёо үүсгэх/засахад шууд цэвэрлэнэ;
   - нийтийн номын каталог — 60 с (HTTP аль хэдийн `public, max-age=300`);
   - уншаагүй мэдэгдлийн тоо — хэрэглэгч тутам 15 с; мэдэгдэл үүсгэх, уншсан болгох
     (`notification-center`, `jobs`) бүрд тухайн хэрэглэгчийнхийг шууд устгана.
   Хэрэглэгчийн хувийн өгөгдөлд HTTP кэш нэмээгүй.
6. **Алдааны буулгалт:** `@prisma/adapter-pg` нь ӨС хүрэхгүй үед `P1001`
   (`DatabaseNotReachable`) KnownRequestError өгдөг байсан тул **500** гоожиж байв
   (локал дээр бодитоор барьсан). Одоо P1001/P1002/P1008/P1017, холболт тасрах,
   socket timeout, холболтын дээд тоо, `statement_timeout` (57014), сервер унтрах
   (57P01–03) → **503** «түр ажиллахгүй». Бусад танихгүй код 500 хэвээр (нуухгүй).
7. **Удаан query-ийн лог:** `DB_SLOW_QUERY_MS` (анхдагч унтраалттай). Прод-д `500`
   гэж тавибал удаан query `WARN slow query …ms`-ээр гарна. `0` = бүх query (локал л).

Шалгасан, өөрчлөх шаардлагагүй: `compression()` асаалттай; хүсэлтийн timeout 60 с;
pool 15, `statement_timeout` 10 с, connect timeout 5 с; ирц тэмдэглэх нь unique түлхүүрээр
upsert тул давтан илгээхэд идемпотент; S3 файл нь presign (сүлжээгүй) → 302; мэдэгдлийн
push/имэйл fire-and-forget.

## Индекс

Шинэ индекс **нэмээгүй**, миграци **байхгүй**. Халуун замын бүх query индекс ашиглана.
`Attempt(classroomId, occurredOn)`-ийг туршсан (200k мөр: 2.3 мс → 0.07 мс) ч зөвхөн
өдөрт нэг удаа ажиллах cron-д хамаатай, одоо байгаа хоёр индекс bitmap-аар хангалттай,
харин хамгийн их бичигддэг хүснэгтэд бичилтийн өртөг нэмэх тул татгалзав.

## Үлдсэн санал (хийгээгүй)

- Ирц тэмдэглэх: сурагч бүрд тусдаа upsert (41 query transaction дотор). Багцлах
  боломжтой ч `onlyIf`/тэмдэглэлийн дүрэм нарийн — тусад нь.
- `auth/me` 5 query: Prisma relation-ийг тусдаа query-гээр татдаг. `relationJoins`
  preview-г асаавал багасна — бүх query-д нөлөөлөх тул тусад нь туршина.

## Ачааллын тестийн цонх (зөвхөн 00:00–01:00)

`k6/README.md`, `STATUS.md` §2 G31. Энэ өөрчлөлтийн дараа заавал харах:

1. Шалгалтын burst: 1000+ сурагч зэрэг `start` → 20 автосэйв → нэг мөчид `submit`.
   Шалгах: submit p95 < 500 мс, HTTP алдаа < 0.5%, `Attempt` давхардалгүй
   (`SELECT "studentId","testId",count(*) … GROUP BY` нь бодлогын тооноос хэтрэхгүй),
   `MistakeEntry` 5–10 минутын дотор бүгд цугласан (`Attempt.mistakeCollectedAt IS NULL` → 0).
2. Ирц: 20 багш зэрэг «Бүгд ирсэн» — pool exhaustion (`P2024`/503) гарахгүй.
3. `DB_SLOW_QUERY_MS=200`-аар асааж лог дээрх удаан query-г цуглуул.

## Deploy-ийн тэмдэглэл

- Миграци байхгүй — `prisma migrate deploy` юу ч хийхгүй.
- Шинэ env (заавал биш): `DB_SLOW_QUERY_MS=500`.
- Дараалал: RDS `pg_dump` → push → deploy скрипт (flock). **18:00–24:00-д deploy хийхгүй.**
- Deploy-ийн дараа: нэг сурагчаар тест эхлүүлж илгээх, «Алдааны дэвтэр» 1 минутын дотор
  дүүрсэн эсэх; мэдэгдлийн тоо уншсаны дараа шууд 0 болох.
- Олон API instance болговол санах ойн кэш instance тутамд тусдаа: мэдэгдлийн тоо
  ≤15 с, томьёо/каталог ≤60 с хоцорч болно (одоо нэг instance).
